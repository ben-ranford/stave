# ADR-017: Percentile performance evidence is reproducible and non-flaky

- Status: Accepted
- Date: 2026-08-12
- Owner: Performance owner
- Proof command: `make verify-performance`

## Context

Stave has explicit p95 budgets, but host load and terminal implementations make
individual timing samples unsuitable as a hard CI pass/fail signal. Conversely,
silently ignoring a regression would make release decisions unreviewable.

## Decision

The checked-in `performance` fixtures run with `GOMAXPROCS=1`, warm each target,
and measure three isolated 101-sample attempts. Reports retain every attempt and
use the lowest p95 as the uncontended component cost. This prevents unrelated
shared-runner scheduling from becoming a product regression while still
failing when all attempts miss. Reports persist invocation, sample-count, host,
runtime, viewport, capability, allocation, and build metadata. Deterministic
and resource invariants fail immediately. A persistent environment-specific
miss requires an explicit ADR and stage downgrade before changing a target.
Idle CPU uses the same three-attempt rule: each window starts after synchronous
garbage collection, all percentages are retained, and the lowest settled window
is compared with the one-core budget. This prevents fixture cleanup from being
misreported as steady-state idle activity.

## Consequences

- Local and CI runs are comparable and auditable without pretending to be a
  cross-host latency guarantee.
- Release owners must attach the report and disposition any budget miss before
  promotion.
- Terminal restore and idle CPU are measured in the core report as
  component/synthetic evidence; live SSH uses the nested adapter's loopback PTY
  performance test and remains separate. Neither is presented as a cross-host
  guarantee.
