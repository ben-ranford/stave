# ADR-018: Lopper is the first proving client, not the framework boundary

- Status: Accepted
- Date: 2026-08-12
- Owner: Architecture owner
- Proof command: `make atlas-check && make schema-freshness && make api-boundary`

## Context

Lopper provides the first migration pressure for Stave, but encoding Lopper's
domain vocabulary, brand, commands, or release lifecycle in the framework
would make the resulting API a private application toolkit rather than reusable
UI infrastructure.

## Decision

Stave's production contracts remain application-neutral. Lopper owns its
strangler adapter and is the first proving client. Atlas is an executable
regression client that composes the root `Program`, action registry, semantic
tree, replay, nine capability profiles, and a different brand. Its checked-in
63-case matrix makes those claims reviewable without Lopper. Shared adapter
fixtures exercise the same surface through optional Bubble Tea and Lip Gloss
modules.

No client receives a privileged API. New clients supply application-owned
models, reducers, views, actions, themes, keymaps, policies, and effects through
the same public contracts.

## Consequences

- Core packages may not import Lopper or any other client domain.
- Lopper-specific migration or rollback work cannot redefine Stave schemas.
- Compatibility claims require the Atlas client and adapter-neutral fixtures to
  remain green alongside Lopper parity.
- New applications use `conformance.CheckClient` with their own semantic
  fixtures, registry, keymap, and capability modes; Lopper fixtures are not a
  prerequisite for adoption.
- A future client can adopt Stave without depending on Lopper packages, assets,
  or command semantics.
